Récapitulatif : quand un merge casse main

Main = prochaine version de prod : un main rouge bloque tout le monde et ne peut plus être livré. Le but est de retrouver un main sain le plus vite possible, sans réécrire l'historique.

Réagir, dans l'ordre

  • Geler les merges dans main, prévenir l'équipe.
  • Ne rien réparer à chaud dans l'environnement : Git reste la référence.
  • Décider en 15 à 30 minutes : revert par défaut.
  • Revert par PR express (git revert), CI verte, priorité sur le verrou DEV.
  • Dégeler quand main est vert en DEV.
  • Réintroduire corrigé, depuis une branche à jour, avec un test qui reproduit la panne.

Revert ou fix-forward ?

  • Revert : cause pas évidente, plusieurs équipes bloquées, ou main en route vers QUALITÉ.
  • Fix-forward : seulement si cause évidente, correctif trivial et CI verte. Même flux qu'un revert, main reste rouge pendant ce temps.
  • Selon l'endroit : DEV, revert ; QUALITÉ, revert et nouveau rc (l'ancien est rejeté, gardé dans Git) ; PROD, rollback par l'image d'abord, puis revert et nouvelle version.
  • Un tag n'est jamais déplacé ni réutilisé.

Prévenir

  • File de merge (merge queue) : tester main + la branche ensemble avant le merge.
  • Branche à jour depuis main avant le verrou DEV, et verrou de courte durée.
  • Gros changement : feature flag désactivé par défaut, ou découpage.
  • Compatibilité des messages Kafka entre versions (rollback possible).
  • Post-mortem sans blâme : on ajoute le test manquant à chaque incident.
⛔ À éviter : laisser main rouge · empiler des merges dessus · corriger à chaud dans l'environnement · reset ou push forcé sur main · supprimer, déplacer ou réutiliser un tag rc · remerger l'ancienne branche sans repartir de main à jour.
