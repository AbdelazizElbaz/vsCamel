Kafka — Changer le nombre de partitions · impact sur le routage et le FIFO

Changer le nombre de partitions : ce qu'il faut retenir

Le code de routage ne change pas (hash(clé) % N), mais quand N change, le résultat change.

Pourquoi ça casse

  • La plupart des groupes changent de partition : environ 80 % de 3 à 5 partitions, 50 % de 3 à 6.
  • Kafka ne déplace pas les messages déjà écrits. Les anciens messages d'un groupe restent dans l'ancienne partition, les nouveaux vont dans la nouvelle.
  • Deux partitions sont lues en parallèle, donc les nouveaux messages peuvent passer avant les anciens (B3 avant B2, D3 avant D2, E3 avant E2).
  • Un groupe peut arriver dans une partition suspendue et se retrouver bloqué par l'erreur d'un autre groupe (le groupe C).
  • La DLQ et le topic de reprise doivent être agrandis en même temps : un message en erreur est copié dans la même partition DLQ, puis republié dans la même partition de reprise.
  • On peut ajouter des partitions, jamais en retirer.

Les solutions

  1. Prévoir large dès le départ (12, 24, 60 partitions) et ajouter des instances de consommateurs au lieu de partitions. Le routage ne change jamais.
  2. Vider avant d'agrandir : mettre les producteurs en pause, vider le topic principal, le topic de reprise et la DLQ, agrandir les trois topics, puis reprendre.
  3. Créer un nouveau topic avec N partitions : finir l'ancien topic avant de lire le nouveau.
  4. Utiliser des paniers fixes : panier = hash(clé) % 1024 ne change jamais, et une table indique la partition de chaque panier. On déplace les paniers un par un, après les avoir vidés.
💡 Le nombre de partitions fixe le parallélisme maximal. Pour grandir sans casser l'ordre, on ajoute des consommateurs, pas des partitions.
